## 二、根因：同一次改动（10-31）埋了两个断点，两个都必须修

### 断点 1：微信被改成必填（已在今天 11-14 修复上线）

commit `9fb1cc0`（2026-10-31，表单优化 + Preview 隔离 + 国家区号自动匹配）把历史逻辑"微信 **或** 电话至少一个"改成了"微信 **必须**"：

- 校验条件从 `if (!wechatVal && !phoneVal)` 变成 `if (!wechatVal)`
- EN/ZH 两个表单都给 `wechat` 加了原生 `required` + 红星
- 同批把 `phone_code` 原生 select 换成 hidden + 自定义国家选择器

Meta / Google 投放的东南亚、非洲、拉美客群里，绝大多数人**没有微信**。浏览器的原生校验会在点击提交时就拦下，连一个 422 都到不了后端。

### 断点 2：数据库缺 3 个列，提交会直接 500（今天 11-14 发现并已修）

同一次 commit 还给 `leads` 表加了 Google Ads 点击 ID 字段，把 `gclid, gbraid, wbraid` 写进了 INSERT 语句，仓库里也有对应迁移 `migrations/0003_add_adclick_ids.sql`——**但这条迁移从来没在生产库执行过**。

实测证据：

```
PRAGMA table_info(leads)  →  没有 gclid / gbraid / wbraid
SELECT ... gclid ... FROM leads  →  SQLITE_ERROR: no such column: gclid
```

后果：任何一次提交走到 `INSERT INTO leads` 就会抛错 → 接口返回 500 `DATABASE_ERROR` → 既不落库、也不发 webhook、也不进表格。**这意味着只修微信必填是不够的，今天之前即使有微信客户提交，也一样会失败。**

已于本日执行 `npx wrangler d1 execute zhongsai-leads --remote --file migrations/0003_add_adclick_ids.sql`，并回读确认三列已存在（`SELECT count(*) FROM leads WHERE gclid IS NULL AND gbraid IS NULL AND wbraid IS NULL` → 42，语句可正常执行）。

> 这条也是"改造后询盘归零"能解释到 0 条、而不是"少量"的原因：断点 1 拦住了不用微信的人，断点 2 拦住了剩下所有能提交的人。

## 三、表格口径：表头不是"和表单不一致"，是"两套表头拼在一起 + 后半截永远空"

### 3.1 现状实测

拉取 `export?format=csv&gid=0` 得到 9155 字节，解析结果：

| 指标 | 实测 |
|---|---|
| 表头列数 | **58 列** |
| 数据行数 | **4 行**（对应 D1 里那 4 条真实线索） |
| 全空列 | **35 列**：第 29–58 列（30 列）全空，另加第 1–28 列里的 5 列（项目用途、UTM Medium/Campaign/Content/Term）也恒空 |
| 每行有值的单元格数 | 20 / 16 / 17 / 19（满值应为 30+） |

58 列的构成是两套 schema 硬拼：

- 第 1–28 列：一套完整字段（线索ID … 提交状态、测试线索）
- 第 29–33 列：人工跟进字段（跟进负责人 / 跟进状态 / 跟进备注 / 最后跟进时间 / 线索性质）
- 第 34–58 列：**把第 4–28 列又抄了一遍**（来源页面、有无图纸、项目国家、区号、电话、微信、身份、项目阶段、项目简述、尺寸、吊车、风荷载、雪荷载、抗震、吊车吨位、设备荷载、留言、附件数、附件下载链接、UTM、落地页、状态）

所以不是"错行"，而是**表头冗余 + 缺列**：前半截能写进去，后半截那套重复表头从建表起就没被写过。

### 3.2 真正在丢的数据（payload 里有，表里永远空）

这些字段官网一直在采集、D1 也存了，但表格第 45–52 列摆着表头却永远是空的：

客户身份（customer_type）、项目阶段（project_stage）、风荷载、雪荷载、抗震要求、吊车吨位、设备荷载、附件数、附件下载链接

对做报价的人来说，**风荷载 / 雪荷载 / 抗震 / 吊车吨位正是决定报价的前置条件**，这几项看不到，等于每次都要回去问客户。

### 3.3 区号和电话为什么会"少字符"

表格里 `+254` 显示成 `254`、`0722103195` 显示成 `722103195`。原因是**写入时被 Google Sheets 当成数字/公式解析**：

- `+254` 以 `+` 开头 → 被当公式 `=254` → 只剩 254
- `0722103195` 被当数字 → 前导 0 丢掉
- 喀麦隆、尼日利亚这类号码尤其容易出问题

D1 里的原值是完整的（`+254`、`+27`、`0722103195`），是表格写入方式吃掉了字符——这是纯技术问题，不是客户填错。

### 3.4 另外三处数据质量问题（不是表头的锅）

| 现象 | 具体 | 判断 |
|---|---|---|
| Keshen 标"有图纸"但附件两列空 | `has_drawings=1`，`lead_files` 里查不到该线索的任何文件 | 当时 upload 没落地，属历史数据缺失，不是表格漏写 |
| monty 国家 Nigeria 但区号 +27 | D1 原值就是 Nigeria + `+27`，邮箱 `@kva.co.za` | 客户在表单里选错国家（或自动匹配取错），表格只是如实反映 |
| 5 个人工跟进列全空 | 4 条真实线索的 跟进负责人/状态/备注/时间/性质 **全部为空** | 线索进来没人认领，这比表头更影响成交 |

## 五、怎么落地（4 步，均在表格里操作，不动网站）

### 第 1 步：新建标签页，导入新表头

1. 在表格里新建一个标签页，命名 **`线索总表`**
2. 用「文件 → 导入 → 上传」，选 `新表头.csv`，导入位置选「替换当前工作表」——这样第一行就是 44 列表头
3. 或者直接把 `新表头.csv` 用文本编辑器打开，复制第一行粘到 A1

### 第 2 步：替换 Apps Script 的写入逻辑

1. 表格 → 扩展程序 → Apps Script
2. **先备份**：把现有 `Code.gs` 全文复制一份存到本地（原有脚本里可能还有邮件通知 / 企微群通知逻辑，不能直接丢）
3. 用 `Apps-Script-写入脚本.gs` 的内容替换 `doPost` 和新增的几个函数；如果原脚本还有通知类函数，在本文件 `doPost` 写表成功之后调用它们
4. 部署：部署 → 管理部署 → 编辑现有部署 → 版本选「新版本」→ 部署。**webhook URL 保持不变**（`LEAD_WEBHOOK_URL` 环境变量不用改）
5. 自检：在 Apps Script 里跑一次 `testBuildRow()`，看日志是否输出 `cols=44 区号=+60 电话=+60 12 345 6789 来源=Google Ads`

脚本里两个关键设计：

- **写值前先把整行设为纯文本**（`setNumberFormat('@')` 再 `setValues`），这是解决 `+254` 变 `254`、`0722103195` 变 `722103195` 的根本办法
- **按 `线索ID` 查重**，同一条线索重复推送不会写两行

`历史4条回填.csv` 已按新表头、用 D1 原值重新生成（区号带 `+`、电话保留前导 0、提交时间已转北京时间、附件链接补全）：
