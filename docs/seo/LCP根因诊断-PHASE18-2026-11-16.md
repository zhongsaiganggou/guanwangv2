## 0. 结论摘要

1. **LCP 不是"默认 Hero 图"**。13 页里：**4 页 LCP 元素是内联 CSS 背景图 DIV**（trusses / agri / about / engineering，且 `initiator=css`），**6 页是 `<img>`**（2 篇博客封面、2 个项目列表卡、项目详情图、2 个首页 hero），**3 页是纯文字**（malaysia、两篇博客在移动端）。同一页面两端还可能换元素：`blog-anchor-bolt-en` 移动端是正文段落（2.00s），桌面端是 756KB 封面图（7.99s）。
2. **真正的瓶颈是"单张 LCP 图体积过大"**，不是 CSS、不是字体（`@font-face`=0）、不是 JS（TBT 58–250ms）。按 CDP 探针的闭合分解，**图片下载时长占 LCP 的 45%–94%，中位约 75%**；其中 4 页 CSS 背景图 + 2 篇博客封面 + 项目卡全部命中这个区间。
3. **"图片发现太晚"只在部分口径成立，本报告不把它当作已证结论**。Lighthouse 模拟把 `blog-crane-zh` 的 6.99s 记作 `load delay`，但 CDP 实测显示该封面在首绘前（1.85s）就已开始下载——两套测量对"发现时机"的判断分歧，**未收敛**。可签发的是：封面 `loading="lazy"`、无 `fetchpriority`、无 `srcset`；背景图只能经 CSS 发现（`initiator=css`）——即**没有任何优先级提升手段**，无论发现早晚都排在低优先级队列。
4. **全站共性**：`<link rel="preload">` = **0 条 / 356 页**（仅首页 hero 有 `fetchpriority=high`）；HTML 全部 `cf-cache-status: DYNAMIC` + `max-age=0, must-revalidate`，不进边缘缓存；内容页 LCP 图除首页外 **100% 为原始 JPEG，无 AVIF/WebP/srcset**；218 个博客页封面共 220 个 `<img>`，**218 个 lazy、0 个 fetchpriority**，按出现次数加权 **166 个（76%）>500KB**（去重后 83/109 也是 76%）。
5. **一处旧口径修正**：CLS **不是全 0**。按 78 次原始跑次重算：`trusses-en` desktop **0.136**、`blog-crane-zh` desktop **0.119**、`blog-crane-zh` mobile **0.091**、`blog-anchor-bolt-en` desktop **0.084**（0.1 为"需要改进"线，三次跑次完全一致，非抖动）。机制与"封面 `img` 无 width/height + CSS `width:100%;height:auto`"一致，但**元素级归因未取得**（`layout-shifts` 审计在本机返回空 items，CDP 未记录 shift sources）。

### 1.4 测量方法与三条硬限制

- **Lighthouse**：`npx lighthouse@11`，`--only-categories=performance`，desktop 加 `--preset=desktop`，未改默认节流；单流串行（先 mobile 39 次、再 desktop 39 次）避免并发污染；每页 3 次取中位。**78/78 成功**。
- **CDP 探针**：Node 零依赖直连 headless Chrome，注入 `PerformanceObserver` 抓 `largest-contentful-paint` + `layout-shift`；`Emulation.setDeviceMetricsOverride`（mobile 412×823 dsf 2.625 / CPU 4x / 150ms·1.6Mbps·750kbps；desktop 1350×940 dsf 1 / CPU 1x / 40ms·10Mbps）+ UA 覆盖 + **`Network.setCacheDisabled(true)`**；3 次/页/设备，78/78。**首轮未禁缓存导致 run2 偏快，已整批废弃重跑。**

**限制 A — Lighthouse 11 在本机有三处审计失效（实测）**：
`largest-contentful-paint-element`、`lcp-lazy-loaded`、`prioritize-lcp-image`、`layout-shifts`、`render-blocking-resources` 均返回 **error 或空 items**（`Cannot read properties of undefined (reading 'frame_sequence')`）。
→ 所以：**LCP 元素一律由 CDP 提供**；**CLS 元素级归因不可得**；**不引用 `render-blocking-resources` 的任何结论**。

**限制 B — 两套测量对"阶段归属"不一致，本报告以 CDP 为阶段依据**：
Lighthouse `metrics` 的四字段（`timeToFirstByte` / `lcpLoadStart` / `lcpLoadEnd` / `largestContentfulPaint`）在本机**无法闭合**：`about-en` mobile 四项相加 4.85s，而 LCP 为 7.50s（残差 2.65s）。CDP 的时间轴则**严格闭合**（`资源开始 + 下载时长 + 绘制 = LCP`：封面页 1.85+14.16+0.04=16.05s，`trusses` 0.65+10.79+0.03=11.47s）。故 §4 用 CDP 做阶段判定，Lighthouse 字段只作交叉参考并如实列出其残差。

**限制 C — 测量网络边界（禁止外推）**：
全部请求从中国境内经跨境链路到 Cloudflare。实证：**边缘命中的 CSS（`cf-cache-status: HIT`、`age` 36.9 万秒、5.8KB）TTFB 仍为 615 / 750 / 763ms**，与 HTML 的 0.75–1.11s 同量级 → **0.6–0.75s 是本机↔Cloudflare 的网络地板**，不能归因于 middleware 或源站。
→ 本报告的 TTFB 与下载时长**高于海外真实用户**；"1MB 图下载 5.5s"不可外推为全球体验；**本轮未取 CrUX 字段数据，海外真实 LCP = unknown**。可签发的只有结构性结论（元素归属、资源体积、lazy/preload/缓存头、模板来源）。

**三条结构性判断（均有源码/审计回链）**

1. **背景图 DIV 无法被预加载扫描器发现**：CDP 的 `initiator` 字段对 4 个页面 × 2 端全部为 **`css`**（资源由 CSS 解析后发现），而博客封面/项目卡/首页 hero 都是 `img`。源码：`src/styles/detail.css:18 .detail-hero-bg{position:absolute;inset:0;background-size:cover;...}`、`src/styles/hub.css:16 .hub-hero-bg{...transform:scale(1.05)}`；页面侧为 `<div class="hub-hero-bg" style="background-image:url('/images/components/steel-truss-hero.jpg')">`。→ 这类元素**不能加 srcset、不能进 `<picture>`、不能用 `fetchpriority`**，也无法被 `preload` 提前（除非手工写 `imagesrcset`）。

**阶段判读**

1. **`下载时长` 是绝对主导**：21 个图片型 LCP 中，下载占 LCP 的 **45%–94%（中位 ≈75%）**；`绘制` 恒为 0.01–1.00s（首页 ZH 的 1.00s 是特例，其资源仅 60KB、下载只用 1.27s）。→ **减小文件体积是唯一能同时改善所有页面的杠杆**。
2. **`发现时机` 不是主导**：`资源开始获取` 普遍在 FCP 之前（0.25–2.06s），即资源并未"排队到很晚"。所以本报告**不签发"发现太晚"**；能签发的是"**没有任何优先级提升手段**"（背景图只能经 CSS 发现，封面被写成 lazy）。这两者不同：前者是时序问题，后者是优先级与可预加载性问题。
3. **文字型 LCP 的瓶颈在首绘**：5 个文字型条目中，LCP 与 FCP 完全相等（malaysia 1.45/1.45、blog-container 1.46/1.46、anchor mobile 2.29/2.29）→ 其全部成本就是"文档→首绘"（CDP 1.45–2.75s，Lighthouse 2.00–4.53s），与图片无关。
4. **Lighthouse 官方四字段与上表不一致**：例如 `about-en` mobile 四字段相加 4.85s vs LCP 7.50s（残差 2.65s）；`blog-crane-zh` mobile 相加 13.99s vs 14.55s（残差 0.56s）。该残差**未归因**，故不用于计算占比——这也是本报告把阶段判定改挂 CDP 的原因。

## 8. CDN / 缓存 / TTFB

### 8.1 HTML 全部不进边缘缓存

| URL | TTFB（3 次） | 关键响应头 |
|---|---|---|
| `/en/about/` | 877 / 1119 / 886ms（body 27.6KB） | `cf-cache-status: DYNAMIC`、`cache-control: public, max-age=0, must-revalidate`、`content-encoding: br` |
| `/en/components/steel-trusses/` | 2070 / 740 / 916ms（31.4KB） | 同上 |
| `/zh/blog/add-crane.../` | 929 / 802 / 756ms（13.7KB） | 同上 |

**机制（可回链源码）**：`functions/_middleware.js` 在静态资源前运行（ROUTES 白名单保护真实路由、尾斜杠/`.html` 归一、旧 URL 301、GONE 410、preview 站 noindex，`import { ROUTES } from './_routes.js'`）→ HTML 每请求进函数路径，`cf-cache-status` 恒为 `DYNAMIC`。

### 8.2 边缘命中仍是 0.6–0.75s（网络地板证据）

`/_astro/index.D-NzDrkv.css`：**750 / 763 / 615ms**，`HIT`、`age` 36.9 万秒、5.8KB、`immutable`。
→ 连 5.8KB 的边缘命中资源都要 0.6–0.75s，**HTML 的 0.8–1.1s 不能归因于 middleware 或源站**。

### 8.3 结论边界

可签发：HTML 不进边缘缓存、图片 TTL 1 天、preload=0、背景图 `initiator=css`。
不可签发：TTFB 高 = middleware 慢；1MB 下载 5.5s = 全球体验；本轮数据 = 海外真实 LCP（无 CrUX 字段数据，`unknown`）。

## 14. 最终七问

**A. 哪些页面 LCP 最差？**
移动端：**博客·加装行车 ZH 14.55s** > trusses 10.29s > agricultural 8.73s > about 7.50s > engineering 7.03s > projects-zh 6.94s > projects-en 6.87s > 汕头立讯 6.85s。
桌面端：**博客·锚栓 EN 7.99s** > 博客·加装行车 ZH 6.50s > trusses 4.92s > about 4.85s。
三页最差的共同点：**LCP 是 772–981KB 的 JPEG**（封面或背景图），且**没有任何优先级提示与响应式变体**。

**B. 最主要的真实瓶颈是什么？**
**单张 LCP 图片的体积**：下载段占 LCP 的 45%–94%（中位 ≈75%），在 21 个图片型 LCP 中 12 个 ≥74%。不是 CSS（`initiator=css` 只说明"发现渠道"，尺寸才是成本）、不是字体（0 个 `@font-face`）、不是 JS（TBT 58–250ms）。次一级是**全站缺 preload + HTML 不进边缘缓存 + 图片只缓存 1 天**，抬高所有页面的起跑线（TTFB 0.75–1.11s，含跨境地板 0.6–0.75s）。

**C. 是否属于全站共性问题？**
部分共性。**共性**：0 preload、HTML `DYNAMIC`、图片 TTL 1 天、非首页图 100% 无 AVIF/WebP。**非共性**：真实拖慢集中在两个模板（博客 218 页、hero-bg 46 页）；首页已被优化（60KB AVIF + high）因此最好；5 个文字型 LCP 条目的瓶颈是"首绘"而非图片。

**D. 是否存在只影响部分模板的问题？**
明确存在：
① **博客模板**（`src/pages/en/blog/[...slug]/index.astro:116` 写死 `loading="lazy"`、无尺寸/priority）→ 218 页；
② **detail/hub hero 模板**（`src/styles/detail.css:18`、`src/styles/hub.css:16` + 各页内联 `background-image`）→ 46 页，`initiator=css` 为机器证据；
③ **项目卡片模板**（lazy + 原图超显示）。
首页不在其中（走 `optimized/home` + `<picture>` 独立路径）。

**E. 最值得先修复的 3 项？**
1. **S1 博客封面**：覆盖 218 页，最大单页收益（772KB→~90KB），并顺带修掉 desktop CLS 0.084–0.119（补尺寸即占位）。

3. **S3 项目卡换档 + S4 图片 TTL 1 年**：两个高频商业列表页，且 TTL 是成本最低的一项改动。
（S5 CSS 合并不进前三：回归面最大且无量化承诺。）

**F. 修复后如何验证？**
同一套脚本、同参数、同串行方式，不换工具不换口径：
- Lighthouse：`%TEMP%\p18\run_lh.ps1 -Device mobile|desktop -OutDir <新目录>`，13 页 ×2 端 ×3 次中位；

**G. 1240 张图片尺寸注入是否仍值得单独排期？**
**不值得单独排期，并入 S1–S3 一起做。** 理由：
1. 它**不解决 LCP**：图片型 LCP 的成本在下载体积（75% 中位占比），与是否标尺寸无因果；首页 hero 有 srcset/尺寸仍 4.62s，其成本是 TTFB+下载。
2. 它**确实与 4 个"页面×端"的 CLS 有关**（0.084–0.136），机制是无尺寸封面 + `width:100%;height:auto`；但这 4 项**全落在博客模板**，做 S1 时补尺寸即一并解决，无需 264 页全站批处理。
3. 全站批处理 1240 张的回归面远大于收益面；且 `trusses-en` desktop 的 0.136 触发元素**尚未定位**，盲注入可能修不到它。
4. 处置：**降级 P3 卫生项**，只在实际改图的页面顺带补齐，并把"新增图片必须带 width/height"写入内容规范。
