# 图片尺寸（width/height）与 CLS —— 方案评审

- 日期：2026-11-16
- 范围：266 项审计中的「1240 个 `<img>` 缺 width/height，264 页，blog 923」
- 结论：**同意「需先评审」，但不同意「CLS 风险」这个定性**。实测 CLS 0.000–0.031（9 页抽样），远低于 0.1 阈值；真正拖慢站点的是 LCP 5.4–8.9s。

---

## 1. 证据基线（本轮实测）

### 1.1 存量结构

| 指标 | 实测值 | 来源 |
|---|---|---|
| HTML 页 | 356 | `dist/**/*.html` |
| `<img>` 总数 | 3660 | 同上 |
| 缺 width 或 height | 1240（33.9%） | 同上 |
| 受影响页 | 264（blog 923、非 blog 317 / 44 页） | 同上 |
| 缺尺寸的唯一 src | 550 | 同上 |
| 其中能在 `public/` 找到真实文件 | **550 / 550** | sharp `stat`+`metadata` |
| 外链、`data:`、SVG 干扰 | 0 | 同上 |

即：**550 个唯一文件全部可解析、全部能读到真实像素宽高，注入面是闭合的，没有未知 src。**

### 1.2 渲染路径（三个来源，不是一处）

| 来源 | 落点 | 现状 |
|---|---|---|
| Markdown 正文图（923） | `src/content/blog/*/*.md` 的 `![alt](/images/...)`，经 `<Content />` 渲染 | 无 dims（`src/pages/en/blog/[...slug]/index.astro:121`） |
| 文章封面（每篇 1 张） | `src/pages/en/blog/[...slug]/index.astro:116` | 无 dims |
| 项目卡/页内字面量（317） | `src/components/ProjectCard.astro:15`、`ProjectDetailLayout.astro:37,161`、以及各页 `index.astro` 里的 `<img>`（全库 357 处字面量，多数已有 dims） | 部分无 dims |

对照：`src/pages/zh/blog/gangjiegou-changfang-zaojia-zhinan/index.astro:71` 等页已手工写了 `width="800" height="450"`，说明站内是**混合作风**，不是全站没做。

### 1.3 CSS 现状（决定注入是否安全）

- `src/styles/global.css:64-67`：`img { max-width:100%; height:auto; }` → 注入 `width/height` 后浏览器按属性算固有比例、`height:auto` 自适应，**不会变形**。
- `src/pages/en/blog/[...slug]/index.astro:229-234`：`.article-body img{max-width:100%;height:auto}` → 同上。
- 固定高容器（如 `home-v3.css:69 .evidence-img img{width:100%;height:380px;object-fit:cover}`）→ CSS 覆盖属性，**注入不改变观感**，但这类图本来就不产生 CLS。

### 1.4 CLS 实测（Lighthouse 11，移动端默认节流）

| 页面 | CLS | LCP | Performance | Lighthouse 判定的「未设尺寸图片」 |
|---|---|---|---|---|
| `/en/blog/steel-structure-anchor-bolt-installation-guide/` | 0.031 | 2.1s | 0.88 | 5 |
| `/en/projects/` | 0.000 | **8.9s** | 0.47 | 0 |
| `/zh/projects/` | 0.000 | 3.8s | 0.80 | 0 |
| `/en/about/` | 0.000 | **8.7s** | 0.61 | 0 |
| `/en/agricultural-steel-buildings/` | 0.000 | 6.8s | 0.56 | 0 |
| `/en/engineering-design/` | 0.000 | 7.3s | 0.61 | 0 |
| `/en/components/steel-trusses/` | 0.010 | 7.7s | 0.72 | 1 |
| `/en/markets/malaysia/` | 0.000 | 7.0s | 0.57 | 0 |
| `/en/projects/shantou-luxshare-electronics-center/` | 0.000 | 5.4s | 0.65 | 0 |

关键读法：**1240 张里，Lighthouse 在 9 个页面上只判定出 6 张「真的影响布局」**。原因是两类：

1. 大量图片处在固定高容器里（`object-fit:cover`），CSS 已锁定盒子高度，不产生位移；
2. 折叠线以下的图在首屏不参与 CLS；滚动后再出现的位移落在「用户输入后 500ms」窗口内，按规范不计。

所以「1240 → CLS 风险」在**效果层面不成立**，它是布局卫生问题，不是性能问题。

## 2. 候选比较（同一组约束：零成本、不得逐页手改、可回滚、中英双语同时覆盖）

### 候选 A：源层面补齐（rehype 插件 + 手改 317 处字面量 + 源扫描门禁）

- 机制：`astro.config.mjs` 加 `markdown.rehypePlugins`，对 md 生成 `<img>` 注入 dims；317 处 astro 字面量逐个补；再加一个扫 `src/**` 的 lint。
- 代价：550 项尺寸表 + 317 处人工编辑（diff 噪声大）；动态 `src={project.image}` 无法静态判定，门禁必须做表达式白名单，误报/漏报都会长期消耗维护精力。
- 失效条件：新页/新文写作时忘记写 dims → 门禁漏过则回归；每次换图要同步改尺寸。
- 否决理由：改动面 317 处、维护成本随发文量线性增长，收益仅为「属性在源码里可见」。

### 候选 B：构建后统一注入（**推荐**）

- 机制：新增 `tools/inject-image-dimensions.mjs`，在 `astro build` 之后、`generate-routes.mjs` 之前跑一遍 `dist/**/*.html`：对每个 `<img>` 满足「缺 width 或 height」且 `src` 以 `/` 开头 → 解析到 `public/` 文件 → sharp 读真实宽高 → 就地插入两个属性；已有属性、外链、`data:`、缺失文件一律跳过并计数。
- 代价：一个脚本（约 80 行）+ `package.json` build 链加一段；不动任何源码与文案。
- 覆盖：md 923 + 封面 + 317 字面量，**一次覆盖全部 1240，且对未来新文章自动生效**。
- 失效条件：Cloudflare 侧对图片做变换导致 served 尺寸与源文件不一致（已查：本站图片由 Pages 原样直出，无图片变换，风险为 0）；`srcset`-only 无 `src` 的图会被跳过（当前 0 例）。
- 回滚：删掉 build 链那一行 → 重新构建即回到现状，**零内容漂移**。

### 候选 C：迁移到 `astro:assets`（`<Image>` / `getImage`）

- 机制：图片移入 `src/assets`，md 改相对引用，模板换 `<Image>`。
- 代价：1000+ 图片迁移 + md 全量引用改写 + `projects-data.ts` 等数据结构变更，同时会改变输出路径与文件名 → 已上线 URL 与外链、GSC 索引全部受影响。
- 否决理由：可逆性差、收益与 B 相同（都是加 dims），但引入 302 重定向与索引风险，属于用 CLAUDE 级手术做创可贴的活。

## 3. 采用合同（候选 B 的精确边界）

1. **只加属性，不改其他**：插入位置在 `src` 之后，保留原有属性顺序、引号风格、`alt`、`loading`、`class`、`style`。
2. **幂等**：两端属性齐全 → 跳过；重复执行 dist 不产生二次插入。
3. **尺寸来源唯一**：`sharp(publicFile).metadata()`；读失败 → 跳过并计入报告，绝不猜。
4. **解析规则**：`src` 以 `/` 开头 → `public/<path>`（去 query）；`http(s)://`、`//`、`data:`、相对路径 → 跳过并计数（当前均为 0）。
5. **产物**：构建末尾打印 `injected: N / skipped: M / unresolved: K`；`K>0` 时构建 **fail**（避免静默漏注入）。
6. **顺序**：`node tools/optimize-home-images.mjs` → `astro build` → `node tools/inject-image-dimensions.mjs` → `node tools/generate-routes.mjs`。
7. **不做的事**：不补 `loading`/`decoding`（已有既有策略，混入会扩大 blast radius）；不改 CSS；不动图片文件；不碰 `404.html`、`oauth-callback.html`（无图，自然跳过）。

## 5. 验证（能推翻方案的动作）

- **能证伪 B 的检查**：把一页里某张 `object-fit:cover` 固定高图取出前后 DOM 对比，若注入后出现盒子高度变化 → 属性与 CSS 冲突，方案需退回只处理「无固定高容器」的图。
- **能证伪「收益为零」的检查**：在弱网（Lighthouse 已用 1.6Mbps/150ms RTT 模拟）下，若注入后某页 CLS 反而升高（因提前分配空间导致后续内容下移）→ 记录并复核该页。
- 数据核对：`dist` 中 `<img>` 缺 dims 数（期望 0）、唯一 src 解析率（期望 550/550）、`npm run seo:check` 仍 PASS、`npm run build` 页数仍 355。

---

## 6. 未闭合项（不得写成已知）

- **真机弱网 CLS**：Lighthouse 节流是模拟，低端安卓 + 4G 冷启下的真实 CLS 未测 → 需要在 GA4/Clarity 侧看分布，本站未接 Clarity，暂为 unknown。
- **LCP 5.4–8.9s 的成因**：Lighthouse 本次未捕获 LCP 元素，无法归因（hero 大图？字体？CSS 阻塞？）→ 属独立诊断项，不能在本方案里顺手猜。
- **Google 是否把 CLS 当同档位排序因子**：本站 CLS 已在绿区，即便补齐也无排序收益，只有「未来布局改动时的保险」价值。

---

## 7. 结论与建议

- **方案层面**：选 B，成本 1 个脚本 + build 链 1 行，可一键回滚，覆盖全部 1240 且自动覆盖未来内容。
- **优先级层面**：**降级为 P3 卫生项**，不要当性能项排期。真正该上 P0 的是 LCP——7/9 抽样页 5.4–8.9s，Performance 0.47–0.80，这才是影响排名与转化的因子。
- 若只做一件事，做 LCP；若要做两件，先 LCP 再上 B（B 不会干扰 LCP 工作，随时可并行）。
